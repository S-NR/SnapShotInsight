How to comply: a brownfield workflow

For an existing product with years of firmware history, use a step-by-step basic TARA (threat analysis and risk assessment). Each step links to the EX-100 output that shows what "done" looks like.

Ground rules

Current state only

Assess the current release branch. No reconstruction of history for old releases.

Collect, don't guess

Every assumption is marked "to confirm" and goes into a question list for the product owner.

Behaviour-preserving fixes

Security changes must not alter measurements, register maps, calibration compatibility or file formats customers rely on.

Evidence as you go

Every step produces a document for the technical file (Annex VII), not a separate audit effort at the end.

The workflow

Scope & classify

In scope? Which class? Who is the manufacturer? Which other CE regimes? → scope checker, classes

System context & trust boundaries (Phase A · A1)

Draw the device, its users, buses, removable media and network links. Mark trust boundaries. → EX-100 context

Assets (A2)

What must be protected: firmware/IP, bootloader, calibration, measurement results, credentials, keys, configuration, logs. Rate C/I/A. → EX-100 assets

Attack surface (A3)

Every interface, including UART, SPI, I2C, JTAG/SWD/ICSP, USB, SD, field buses and UI. Verify on hardware. → EX-100 interfaces

SBOM (A4)

Recover components and versions from source headers; output CycloneDX JSON; start CVE monitoring. → EX-100 SBOM

First risk matrix (A5)

Likelihood × impact for each threat-to-asset pair; agree the method with the client. → EX-100 matrix

Code review against Annex I

Look for unsigned updates, debug ports, default passwords, unbounded parsers, missing integrity checks. → EX-100 findings

Treat first issues

Quick wins first (low effort, high value), then planned measures with estimates. → quick wins

Phase B: STRIDE threat modelling (B1)

Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege, per interface. → EX-100 STRIDE prep

Process & documentation

CVD policy, reporting runbook, support period, Annex II user info, Annex VII technical file, DoC. → obligations

Where AI tooling helps

AI assistants (Claude, ChatGPT, Copilot) do not replace the engineer's judgement, but they speed up the evidence-heavy steps:

Understand

Attack-surface mapping

Read a large legacy tree, list every interface, parser and config bit with file/line evidence. EX-100's 9 interfaces were mapped this way.

Inventory

SBOM recovery

Find third-party components and versions from headers and project files, then draft CycloneDX.

Review

Security code review

Flag unbounded copies, hard-coded secrets, weak RNG, disabled protections. Every hit is verified by a person.

Impact

Change impact analysis

Before a fix: what else reads this buffer, register map or MRAM layout? Protects brownfield behaviour.

Respond

24-hour triage

Match a new CVE against the SBOM per release and draft the early-warning report.

Document

Technical file drafts

Turn findings into risk registers, Annex II text and test plans for review.

GuardrailsDo not paste customer source into tools without the client's approval. Keep a human approval gate (G1) before any change. Mark AI output as draft until verified.
