S1: Secure bootloader with Nitrokey (feasibility)

Result: feasible, with the right split of roles. The PIC32MX575 has no hardware secure boot and no crypto engine, so secure boot means:

Immutable bootloader

Bootloader region write-protected (PWP/BWP) and CP = ON.

Public key in the bootloader

Integrity-critical, not secret.

Verify before programming

ECDSA P-256 signature verified in software (micro-ecc, BSD; or wolfCrypt) before erase/program.

Anti-rollback

Version counter in protected storage.

Signing flow on the release PC

MPLAB X build"Execute this line after build"
→
hex → binFixed image layout
→
SHA-256Hash on the host
→
Nitrokey HSM 2Sign hash with CKM_ECDSA via PKCS#11/OpenSC
→
Update fileHeader + image + signature
Nitrokey detailHash on the host and sign with CKM_ECDSA. Using CKM_ECDSA_SHA256 on the whole image fails above about 1 KB of input (OpenSC issue #2469, Nitrokey forum).
OptionProsCons
Nitrokey HSM 2 (recommended)Mature PKCS#11, on-device P-256 key generation, DKEK n-of-m backupSigning-size limit (hash on host)
Nitrokey 3 (PIV/PKCS#11)Works per user reportsCheck PIV maturity in stable firmware

PoC must confirm: verify time and code size on PIC32MX at 72 MHz (must fit 52 KB); one-time field update from BL 0.0.4; key ceremony and backup; OpenSC on the build PC.

Full implementation (2027): ≈ 120–200 h covering bootloader rework, update format, anti-rollback, production config bits, key ceremony, migration of installed BL 0.0.4 units, and tests incl. power-fail during update. Depends on bootloader source (Q-01).

Interim measures until secure boot (≈ 16–24 h, part of Q1)

  • Production config bits: CP = ON, PWP on bootloader pages, BWP = ON, JTAG disabled at startup.
  • Update only after a service-level confirmation in the UI (needs bootloader source).
  • Image integrity check (SHA-256/CRC32): catches corruption, not tampering. Document as such.
  • Update procedure and residual risk in user/service information.

Phase B: STRIDE preparation

The client's generic examples mapped to DWC2's real architecture (B1, 24–40 h, after first issues are treated):

STRIDEClient exampleDWC2 equivalent to analyse
SpoofingFake update serverNo update server: the threat is a fake update file on SD/USB. Also spoofed Modbus/M-Bus masters and converter config frames
TamperingModified image in external SPI flashFirmware is in internal flash (via SD bootloader or JTAG/ICSP). The external SPI device is the MRAM with calibration
Repudiation—No security log: changes cannot be attributed
Information disclosureReading flash via JTAGApplies: JTAG not disabled, CP off. Also PIN from protect.dwc
Denial of serviceMalformed network packetsNetwork only via converter. Also malformed frames and malformed SD files (confirmed overflow)
Elevation of privilege—Master PIN, optional PIN, no role model (S2)
