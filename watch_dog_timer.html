🛡️ Watchdog Timer in Embedded Systems

What is a Watchdog Timer?

A Watchdog Timer (WDT) is a hardware timer that resets the system if software crashes. It ensures the firmware is operating properly by expecting periodic "refresh" signals from the code.

a. How It Works

  1. WDT starts counting down from a preset value.
  2. The program must reset the WDT regularly.
  3. If it isn't reset in time, it assumes failure and reboots the system.

b. Example Scenario

  • MCU controls a motor but gets stuck due to a bug.
  • The WDT isn’t refreshed, so it resets the system automatically.

Types of Watchdog Timers

a. Independent Watchdog Timer (IWDG)

  • Uses internal LSI (low-speed clock).
  • Works even if the main clock fails.
  • Cannot be disabled once started.
  • Used in critical systems.

Reference Code:

  • IWDG_PRESCALER_64 — sets prescaler speed
  • 4095 — max reload value
  • HAL_IWDG_Refresh(&hiwdg); — refreshes WDT

b. Windowed Watchdog Timer (WWDG)

  • WDT must be refreshed within a narrow window
  • Refresh too early or too late = reset
  • Used to detect faulty execution timing

Key Considerations

  • ✅ Choose timeout wisely: too short = false resets; too long = delayed fault detection
  • ✅ Ensure WDT is refreshed periodically
  • ⚠️ Some WDTs (like IWDG in STM32) cannot be stopped
  • ✅ WWDG helps detect timing issues

Applications

  • 🚑 Medical Devices
  • 🚗 Automotive ECUs
  • 🔧 IoT & Industrial Systems
  • 🚀 Satellites & Drones

Prescaler & Reload Value

Prescaler and reload determine the timeout duration before the WDT resets the system.

Timeout Formula

Timeout = (Reload + 1) / (Clock / Prescaler)

= (4095 + 1) / (32,000 / 4)   = 0.512 sec
= (4095 + 1) / (32,000 / 64) = 8.192 sec
= (2999 + 1) / (32,000 / 32) = 3 sec

Practical Use Cases

Case 1: Short Timeout for Critical System

  • Prescaler: 16
  • Reload: 1000
  • Timeout: 0.5 sec
  • ✅ Used for motor control

Case 2: Long Timeout for Low Priority

  • Prescaler: 256
  • Reload: 4095
  • Timeout: 32 sec
  • ✅ Ideal for IoT sleep-mode apps

Time selction for WDT

The best time configuration for a Watchdog Timer (WDT) really depends on your application and how often your system can safely be expected to refresh the watchdog.
There isn’t a single "universal" best time — instead, you balance safety (resetting quickly if stuck) and practicality (not resetting during normal long operations).

General Guidelines

  • WDT timeout > longest expected blocking task:
    Pick a timeout slightly longer than your worst-case execution time of the main loop, task, or critical function. Example: If your loop normally takes 50 ms but can occasionally take 200 ms, set WDT ≥ 300 ms.
  • Avoid too short timeouts:
    If set too short, normal delays (e.g., communication wait, flash writes, sensor response) may falsely trigger resets.
  • Avoid too long timeouts:
    If set too long, it defeats the purpose — the system may stay stuck for several seconds before recovery.
  • ✅ Used for motor control

Typical Ranges

  • Real-time / safety-critical (motor control, medical, etc.):
    10 ms – 500 ms (Fast recovery is required. Usually paired with a window watchdog.)
  • General embedded systems (sensors, communication, IoT):
    100 ms – 2 s
  • Systems with long transactions (flash writes, firmware updates, slow comms):
    1 s – 10 s

Practical Tip

Many designs use:
  • Main loop / RTOS task runs every 10–100 ms → WDT = 500 ms to 2 s
  • Heartbeat or periodic ISR “kicks” to refresh WDT
  • Sometimes window WDT (must refresh within a time window, not too fast or too slow) for better fault detection

Set WDT to about 2× the maximum expected execution time of your longest normal operation.
